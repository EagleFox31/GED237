# LESSON-2026-076 — Relecture d'un écran : vérifier le contrôle de droits de chaque route, pas seulement son filtre

- **Date :** 2026-11-19
- **Catégorie :** process / relecture / autorisations
- **Statut :** open. La grille de relecture est complétée. Le correctif de l'écran, une route dédiée dans #445 et #453, est en cours : il reste à rejouer le parcours au navigateur avec le profil chef de service.
- **Liens :** PR #453 (remplaçants du même service), PR #445

**Contexte** — #453 remplit la liste « Agent absent » de l'écran des absences avec `GET /api/v1/users/`. Utilisateur visé : le chef de service (rôle `manager`).

**Échec / near miss** — Relecture de code validée sur 6388bdec : « GET /users déjà limité au service pour manager ». Au contre-test navigateur, le chef de service reçoit 403 : la liste reste vide et il ne peut déclarer aucune absence.

**Cause racine** — `read_users` appelle d'abord `authorize_or_403(current_user, "users", "read")`. Dans `policy.csv`, `users:read` n'est accordé qu'à `unit_admin` et `auditor`, et `users:manage` qu'aux administrateurs. La branche qui limite `manager` et `reader` à leur service, plus bas dans la même fonction, ne s'exécute donc jamais pour eux. La relecture a lu cette branche, en a conclu que le rôle était servi, et n'a pas vérifié le contrôle placé avant ni la politique.

**Classification** — Erreur de relecture, de méthode. La branche morte rend l'erreur facile : son code laisse croire que le rôle est autorisé. Aucun test ne jouait la route avec ce rôle.

**Résolution (en cours)** — Pas de nouveau droit `users:read` pour `manager`, car `UserRead` en dirait trop. Une route dédiée, dans #445, liste les agents que le chef de service peut déclarer absents. Son périmètre est exactement celui de la création d'absence, et elle ne renvoie que l'identifiant, le nom affiché et le service. #453 l'utilise. Pour passer au statut `resolved` : parcours rejoué au navigateur avec le profil chef de service, sur une branche qui réunit #445 et #453.

**Prévention** —
- Grille de relecture : pour chaque route appelée par un écran, vérifier le contrôle de droits pour le rôle visé, c'est-à-dire `authorize_or_403` ou `can_perform`, et la ligne de `policy.csv` qui accorde le droit. Ne pas s'arrêter au filtrage.
- Si le parcours n'a pas été joué avec ce rôle, l'écrire dans l'avis : « OK code, non joué au navigateur, profil X non vérifié ».
- Pour une route ajoutée ou modifiée pour un rôle donné, au moins un test API avec ce rôle qui vérifie le code de retour (200), et pas seulement le contenu.

**Leçon généralisée** — Un filtre par rôle écrit dans une fonction ne prouve pas que ce rôle passe le contrôle d'entrée de la route. Relire une autorisation dans l'ordre où elle s'exécute : d'abord le contrôle, puis la politique, puis le filtre. Un rôle n'est réellement servi que lorsqu'une requête faite avec ce rôle a répondu.
