# LESSON-2026-075 — `git push` sans destination depuis un worktree : le push suit la branche de base

- **Date :** 2026-11-19
- **Catégorie :** process / git
- **Statut :** resolved (`push.default=nothing` dans la configuration du dépôt, refspec explicite)
- **Liens :** PR #467 (`ci/lessons-register-frozen`), PR #435 et #468, ruleset GitHub 26190959 sur `main`

**Contexte** — Les sessions travaillent dans des worktrees séparés, créés par `git worktree add -b <nouvelle branche> <chemin> <branche distante>`, puis poussent avec `git push -u origin <nouvelle branche>`. Le dépôt était en `push.default=upstream`.

**Échec / near miss** — Deux cas le même jour, même cause :

1. Worktree créé depuis `origin/main`. Git a répondu `ci/lessons-register-frozen -> main (non-fast-forward)` : le push visait `main`. Ce push direct était refusé dans tous les cas : `main` est protégé par le ruleset 26190959 (passage par PR obligatoire, sans contournement). Le message affiché venait seulement de ce que `main` avait avancé entre-temps (103ce48b). `main` n'a pas bougé.
2. Worktree créé depuis `origin/feat/v11-audit-export-actors` (branche de #435) pour une PR empilée. Aucune protection sur cette branche : le commit 23813272 y a été écrit et s'est retrouvé dans #435, une PR d'une autre session. La sortie du push était filtrée (`-q`, `grep -v`), la ligne `1d96f8f0..23813272 -> feat/v11-audit-export-actors` n'a pas été vue ; l'erreur est apparue à `gh pr create` (« No commits between »), confirmée par `git ls-remote`.

**Cause racine** — `worktree add -b X <branche distante>` règle cette branche distante comme branche suivie de `X`. Avec `push.default=upstream`, `git push origin X` pousse vers la branche suivie, pas vers une branche nommée `X` : le nom écrit dans la commande donne l'impression de fixer la destination, alors que Git la déduit de la configuration.

**Classification** — Erreur de procédure répétée (deux sessions). Garde-fou serveur présent seulement sur `main` ; aucun garde-fou local ; sortie de push filtrée.

**Résolution** — Cas 1 : push refait avec `git push origin HEAD:refs/heads/ci/lessons-register-frozen`. Cas 2 : commit inverse a54be1d0 sur la branche de #435 (contenu identique à 1d96f8f0, diff vide vérifié, sans push forcé), travail ré-appliqué par cherry-pick sur sa propre branche (a8533b37) poussée avec un refspec explicite ; propriétaire de #435 prévenu.

**Prévention** —
- Contrôle vérifiable : `git config --get push.default` répond `nothing` dans la configuration du dépôt (partagée par tous les worktrees). Un `git push` sans destination échoue au lieu de deviner.
- `bash scripts/check-git-safety.sh` dans chaque worktree avant un premier push : il échoue si `push.default` n'est pas `nothing` ou si la branche courante suit une branche d'un autre nom. Ses tests (`scripts/test_check_git_safety.sh`) tournent en CI.
- Toujours pousser avec une destination explicite : `git push origin HEAD:refs/heads/<branche>`.
- Créer les branches de worktree avec `--no-track` (`git worktree add --no-track -b <branche> <chemin> <base>`) ; avant un premier push, `git rev-parse --abbrev-ref @{upstream}` ne doit pas répondre la branche de base.
- Ne jamais filtrer la ligne `ancien..nouveau -> ref` d'un push ; vérifier avec `git ls-remote` avant `gh pr create`.
- Garde serveur existante : ruleset 26190959 (PR, contrôles requis, ni suppression ni push forcé sur `main`) ; elle ne protège pas les branches des autres PR.

**Leçon généralisée** — Ne jamais laisser Git déduire la destination d'un push. Une branche créée depuis une autre (branche par défaut ou base d'une PR empilée) en hérite le suivi, et une commande « habituelle » peut écrire sur une branche qui n'est pas la sienne. Une erreur répétée appelle un contrôle plus fort : une configuration qui refuse le push implicite.
