Innovateur, 2026-11-10, lu sur `EagleFox31/appfactory-project-automation` v1.4.0 (`README.md` § « Reusable release automation », `examples/product-release.yml`, `.github/workflows/reusable-release.yml`) et sur GED237 `main` d34d51b. Pas avant la démo : c'est un changement de CI pendant le gel (surface `ci-platform` de `appfactory-impact.json`).

1. **Décision : Adopt, avec une adaptation** — appeler `reusable-release.yml` épinglé sur le SHA revu de `v1` (`0523510a8e42290df3bae5749d034b1637569af5` = v1.4.0, à revérifier le jour J), `release-type: simple`, `target-branch: main`, `path: .` ; rien de spécifique produit (ni .NET ni Tauri).
2. **Ce qui s'ajoute** : un seul fichier `.github/workflows/release.yml` (copie de `examples/product-release.yml`, déclenché sur `push: main` + `workflow_dispatch` avec `release_as`) ; Release Please tient une PR de release à partir des titres de commit conventionnels (`feat:`, `fix:`, `docs:` déjà en usage sur `main`) ; sa fusion crée le tag `vX.Y.Z` et la release GitHub.
3. **Permissions** : `contents`, `issues`, `pull-requests` en écriture pour le job ; **secret `APPFACTORY_RELEASE_TOKEN` nécessaire** (ou l'App `broker-user` déjà utilisée par l'automatisation Project) : avec `GITHUB_TOKEN` seul, la PR de release ne déclenche aucune CI, or la gouvernance exige le check `CI Gate` (`project-config.json`) : la PR serait infusionnable.
4. **Adaptation** : `release-please-config.json` + `.release-please-manifest.json` (entrée `config-file`) pour les sections en français (`changelog-sections` : Fonctionnalités, Corrections, Recette et CI, Documentation) ; sinon Release Please écrit « Features / Bug Fixes » en anglais au-dessus de notre `CHANGELOG.md`.
5. **CHANGELOG.md** : Release Please **préfixe** le fichier existant, il ne l'écrase pas ; l'entrée manuelle `[1.0.0-rc.1]` du 24/11 reste et sert d'amorce : le manifeste part de `1.0.0-rc.1` et la première PR de release propose `1.0.0` (ou `release_as` pour forcer).
6. **`release-integrity.yml`** : inchangé ; il se déclenche sur `release: published`, donc sur chaque release créée par Release Please (SBOM, manifeste, signature GPG si le secret existe). Rien à modifier.
7. **`APP_VERSION`** : inchangé ; `docker-compose.yml:139` lit `${APP_VERSION:-0.0.0-dev}` : le déploiement continue de passer le tag ; une suite possible est de l'injecter dans l'image à la publication (`reusable-container-build.yml`, hors périmètre ici).
8. **Gouvernance D5** : la suppression automatique des branches fusionnées (décision PO) s'applique aussi aux branches `release-please--branches--main`.
9. **Coût** : ≈ 0,25 j de session (workflow, config, secret posé par le PO, un `workflow_dispatch` d'essai) ; preuve = PR de release ouverte avec le bon CHANGELOG, puis un tag `v1.0.0` créé par fusion.
10. **Risque** : un titre de PR non conventionnel sort du CHANGELOG généré (déjà le cas de #15, #61) ; règle à ajouter au modèle de PR : titre `type(scope): sujet`.
